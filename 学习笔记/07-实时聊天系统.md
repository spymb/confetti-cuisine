# 第七课：实时聊天系统（Socket.io）— 学习笔记

## 一、本课概览

在第六课 RESTful API 的基础上，引入第三种通信协议 —— **WebSocket**，实现已登录用户的实时群聊。项目从"请求-响应"的单向通信升级为**全双工持久连接**，同时处理 HTTP、WebSocket 两条协议通道在同一个进程内的共存问题。

| 主题 | 核心内容 |
|------|---------|
| WebSocket 通信 | Socket.io 事件驱动模型（`emit` / `on`）、房间广播（`io.to(room).emit()`） |
| 协议原理 | Upgrade 握手（101 Switching Protocols）、一个端口跑 HTTP + WebSocket 两种协议 |
| 通用流程 | `io`（总机）vs `socket`（分机）、七步使用流程、ack 确认、自动重连与可重入 |
| Session 共享 | `wrapSession()` 适配器 —— 让 express-session 中间件在 Socket.io 上下文工作 |
| Socket 认证 | 从 `socket.request.session.passport.user` 取 ID → 查库 → 挂 `socket.data.user` |
| 消息持久化 | Message 模型 + `userName` 冗余存储 + 最近 20 条历史加载 |
| 安全边界 | 用户身份只从 Socket 握手获取，绝不写入 HTML 模板或全局 JS 变量 |
| 跨标签页通信 | `localStorage` + `storage` 事件实现未读消息闪烁提醒 |
| 系统集成 | `app.listen()` 显式化为 `http.createServer(app)`，CSP 放行 `ws:`/`wss:` |

## 二、为什么需要 WebSocket

### HTTP 的局限

前五课的所有交互都是 HTTP 模式：**一问一答，结束即断**。

```
HTTP：  客户端 请求→  ←响应 服务器（每次都要重新建立连接）
```

如果要用 HTTP 实现聊天，只能**轮询**——客户端每隔几秒问一次"有新消息吗"，大部分请求返回空，浪费严重。

### WebSocket 的模式

```
WebSocket：客户端 ⇄ 服务器（建立一次连接，持续双向推送）
```

建立连接后，服务器可以**主动**把新消息推给所有在线客户端，无需客户端不断询问。这就是"实时"的含义。

Socket.io 在原生 WebSocket 之上做了封装：自动降级（WebSocket 不可用时退回 HTTP 长轮询）、自动重连、事件命名空间、房间管理。

### 为什么不直接用原生 WebSocket

| 能力 | 原生 WebSocket | Socket.io |
|---|---|---|
| 断线自动重连 | ❌ 自己写 | ✅ 内置 |
| 房间（room）分组广播 | ❌ 自己管理连接列表 | ✅ `socket.join()` |
| 消息确认（ack 回调） | ❌ 自己设计协议 | ✅ 内置 |
| 降级方案（退回长轮询） | ❌ | ✅ 自动 |

### WebSocket 握手：从 HTTP"变身"而来

WebSocket 连接不是凭空建立的，**握手阶段本身就是一次 HTTP 请求**：

```
浏览器 → 服务器: GET /socket.io/ HTTP/1.1
                Upgrade: websocket              ← "我想升级协议"
                Connection: Upgrade

服务器 → 浏览器: HTTP/1.1 101 Switching Protocols ← "同意，切换！"
```

从这一刻起，这条 TCP 连接**不再说 HTTP**，切换成 WebSocket 协议，保持不断开，双方随时互发数据帧。

由此得出准确图景：**一个服务器、一个端口、两种协议，握手时决定说哪种**。

- 请求刚开始都是 HTTP，服务器看有没有 `Upgrade: websocket` 头决定交给谁：有 → Socket.io 接管；没有 → Express 路由处理。
- `new Server(httpServer)` 不是另起服务器，只是往已有服务器上**注册一个监听器**，专门拦截路径为 `/socket.io/` 且带 Upgrade 头的请求。Express 看不到这些请求，普通页面请求 Socket.io 也不碰。

## 三、Socket.io 通用使用流程

### 心智模型

`io` 是**总机**（管所有连接），`socket` 是**分机**（一个浏览器连接）。两端 API 完全对称：`emit` 发送、`on` 监听，事件名自定义，约定俗成用 `命名空间:动作` 风格（`chat:message`），避免撞名。

写 Socket.io 代码的本质就是**设计一张事件协议表**，双方各自挂监听器，谁有事谁 emit。

### 七步流程

```ts
/* ── 服务端 ── */

// ① 挂到 HTTP 服务器（app.listen() 要拆开）
const server = createServer(app);
const io = new Server(server);
server.listen(3000);              // listen 的是 server，不是 app

// ② 中间件：每个新连接先过这里，可拒绝
io.use((socket, next) => {
  if (验证通过) next();
  else next(new Error('Unauthorized'));
});

// ③ 监听连接，给每个连接注册事件（回调对每个客户端独立执行一遍）
io.on('connection', (socket) => {
  socket.on('chat:message', (data) => { /* ... */ });
  socket.on('disconnect', () => { /* ... */ });
});
```

```html
<!-- ④ 客户端：服务端自动提供这个文件，不用自己下载 -->
<script src="/socket.io/socket.io.js"></script>
<script>const socket = io();</script>   <!-- 同源连接，不用传参 -->
```

```js
/* ⑤ 双方 emit / on 互发 */
socket.emit('chat:message', data);            // 客户端发
socket.on('chat:message', (data) => ...);     // 客户端收（服务端 emit 的）

/* ⑥ 按需：房间 / ack / 定向发送 */
socket.join(room);                            // 进房间
io.to(room).emit(...);                        // 房间所有人（含自己）
socket.to(room).emit(...);                    // 房间其他人（不含自己）
socket.emit(...);                             // 只发这个客户端

// ack：前端想知道"发成功没"
socket.emit('chat:message', data, (res) => { if (res.ok) ... });  // 客户端
socket.on('chat:message', (data, ack) => ack({ ok: true }));      // 服务端

/* ⑦ 断开 */
socket.on('disconnect', (reason) => { /* 清理状态、广播离开 */ });
```

### 三条重要约定

1. **客户端不本地回显**：发消息后不在本地手动追加气泡，等服务端广播回来统一渲染——否则自己渲染一遍 + 广播一遍，消息出现两次。
2. **断线重连不用自己写**：Socket.io 客户端自动重试，重连成功会**再次触发**服务端的 `connection`——所以 `connection` 里的逻辑必须**可重入**（重新发身份、重新进房间，本课代码就是这么设计的）。
3. **`connection` 回调对每个客户端独立执行**：里面注册的所有 `socket.on(...)` 只对这个连接生效。

### 附：`socket.data` 的 TypeScript 类型扩展

每个连接有个 `socket.data` 口袋（连接期间随便存）。用**模块扩展**语法告诉编译器口袋里有什么：

```ts
declare module 'socket.io' {
  interface SocketData {
    user?: { _id: ObjectId; name: string; email: string; role: 'admin' | 'user' };
  }
}
```

之后 `socket.data.user.name` 就有类型检查。本课在 `authMiddleware` 里写入，在 `connection` 回调里读取。

## 四、Session 共享 —— 本课最精妙的设计

### 问题

HTTP 路由里的认证靠 `req.user`（Passport 从 session 反序列化）。但 WebSocket 连接不走 Express 路由管线，`socket.request` 上**没有** `req.user`。

### 解法：包装 express-session 中间件

[src/chat/index.ts](../src/chat/index.ts) 的 `wrapSession()`：

```ts
function wrapSession(middleware) {
  return (socket, next) => {
    const res = { /* 最小化 Mock Response */ } as unknown as Response;
    middleware(socket.request as any, res, next);
  };
}
```

**原理**：浏览器发起 WebSocket 握手时携带和 HTTP 请求**完全相同的 cookie**（同源）。express-session 中间件只依赖 `req.headers.cookie` 来加载会话——给它一个 Mock 的 Response 对象糊弄过去（`saveUninitialized: false` 保证不会尝试写入响应），session 数据就挂到了 `socket.request.session` 上。

这是**适配器模式**的实际应用：同一个中间件，通过包装适配到不同的调用环境。

### 认证链路对比

```
API 路由（第六课）：
  HTTP Request → cookie → express-session → req.session
    → Passport deserializeUser 自动查库 → req.user ✓

WebSocket（本课）：
  WS Upgrade Request → 同一个 cookie → wrapSession() → express-session
    → socket.request.session.passport.user (ID)
      → authMiddleware 手动查库 → socket.data.user ✓
```

两条路径的根都在**同一个 MongoDB Session Store**，拿到的也是同一个用户。区别只是：API 路由有 Passport 自动做反序列化，WebSocket 要手动做一遍。

## 五、安全边界：谁做判断，谁拿身份

### 核心原则

> **谁做判断，谁拿身份。** 服务端做判断 → 服务端拿身份。客户端做判断 → 客户端需要身份，但只能从安全通道拿。

### 其他页面 vs 聊天页

| | 其他页面（HTTP） | 聊天页（WebSocket） |
|---|---|---|
| 模板里的用户信息 | `<%= locals.user.name %>` 渲染到 HTML | 故意不传 |
| 身份判断位置 | **服务端**（`req.user` / `req.jwtPayload`） | **客户端**（`myUserId` 决定气泡左右） |
| 暴露风险 | 暴露了也没用——服务端写操作不读客户端变量 | 暴露了就有用——恶意用户改 `myUserId` 可混淆 UI |
| 身份来源 | 模板不需要（展示用 `res.locals.user`） | `socket.on('chat:identity')` 服务端握手后推送 |

### 关键实现

**控制器刻意不传用户数据**（[chatController.ts](../src/controllers/chatController.ts)）：

```ts
res.render('chat', {
  title: '聊天室',
  currentPage: 'chat',
  pageScript: { ... },
  // 没有 currentUser、没有 userId
});
```

**服务端在连接建立后推送身份**（[chat/index.ts](../src/chat/index.ts)）：

```ts
socket.emit('chat:identity', {
  userId: String(user._id),
  userName: user.name,
});
```

**客户端存闭包变量而非全局**（[chat.js](../public/js/chat.js)）：

```js
let myUserId = null;
socket.on('chat:identity', (data) => { myUserId = data.userId; });
```

三者配合：`myUserId` 不存在于 HTML 源码里、不在 `window` 上、来自服务端 WebSocket 推送。这比写在 `<script>window.me = ...</script>` 安全一个层级。

> 严格来说，客户端终究不可信（断点调试可改内存），但这个设计的意义在于**不主动把枪递出去**。

## 六、事件协议设计

### 双向事件表

`index.ts`（服务端）和 `chat.js`（客户端）通过**约定的事件名**通信，彼此不知道对方实现细节：

| 事件名 | 方向 | 载荷 | 用途 |
|---|---|---|---|
| `chat:identity` | server→client | `{ userId, userName }` | 告诉客户端"你是谁"（只发一次） |
| `chat:history` | server→client | `Message[]` | 最近 20 条历史（连接后自动发） |
| `chat:message` | client→server | `{ content }` | 用户发送消息（带 ack 回调） |
| `chat:message` | server→client | `{ _id, userId, userName, content, createdAt }` | 广播新消息（房间内所有人，含自己） |
| `chat:user-joined` | server→client | `{ userName, timestamp }` | 广播有人加入（不含自己） |
| `chat:user-left` | server→client | `{ userName, timestamp }` | 广播有人离开 |
| `connect_error` | — | `Error` | 客户端捕获 Unauthorized → 跳登录页 |

### 广播的三个 API

```ts
socket.emit(...)           // 只发给这个连接自己（如 chat:identity、chat:history）
io.to(ROOM).emit(...)      // 发给房间内所有人（含自己）
socket.to(ROOM).emit(...)  // 发给房间内除自己外的其他人
```

消息广播用 `io.to`（自己也要看到确认回显），加入/离开通知用 `socket.to`（自己不需要被通知"你加入了"；断开时反正自己也收不到）。

### 一条消息的完整生命周期

```
用户 A 输入"你好" → form submit
  → chat.js: socket.emit('chat:message', { content }, ack)
    → WebSocket → index.ts: socket.on('chat:message')
      → 校验非空 → Message.create() 存 MongoDB
      → io.to(ROOM).emit('chat:message', payload) 广播
        → 用户 A 的 chat.js: socket.on('chat:message') → 右对齐气泡
        → 用户 B 的 chat.js: socket.on('chat:message') → 左对齐气泡
      → ack({ ok: true }) → chat.js 清空输入框
```

## 七、Message 模型设计决策

### 字段命名：`user` 而非 `userId`

```ts
user: { type: Schema.Types.ObjectId, ref: 'User' }
```

遵循 Mongoose 社区惯例：外键引用用实体名（`user`、`course`），与项目已有的 `enrolledCourses`（不叫 `enrolledCourseIds`）、`subscriberProfile` 保持一致。populate 后 `message.user.name` 语义自然。

### 冗余存储 `userName`

**用写入换读取**：广播消息时每个客户端都要显示发送者名字。如果不冗余，每条消息都要 `populate('user')` 多查一次库。聊天消息写一次、读多次（每个人进聊天室都加载历史），冗余值得。

### 两个索引的理由

```ts
messageSchema.index({ createdAt: -1 });              // ① 全站聊天室
messageSchema.index({ courseId: 1, createdAt: -1 }); // ② 课程群聊（预留）
```

MongoDB 复合索引遵循**最左前缀原则**：索引 ② 以 `courseId` 开头，全站查询（无 courseId 条件）用不上它；索引 ① 不含 `courseId`，课程查询用不上它。两个场景各配一个，不能合并。

### 不需要软删除

对比 Course 的软删除机制（被 `User.enrolledCourses` 引用，真删会产生悬挂 ID）。Message **没有任何其他表的外键指向它**，所以可以直接真删。判断标准：**有没有其他表的字段引用我？没有 → 真删。**

## 八、main.ts 集成的三个坑

### 坑 1：`app.listen()` 是语法糖

```ts
// ❌ 之前：内部创建隐藏的 server，Socket.io 拿不到
app.listen(PORT, callback);

// ✅ 现在：显式创建，同时挂载 Express 和 Socket.io
const server = createServer(app);
setupChat(server, sessionMiddleware);
server.listen(PORT, callback);
```

### 坑 2：session 中间件必须提取为变量

```ts
// ❌ 之前：内联使用，chat/index.ts 无法引用
app.use(session({ ... }));

// ✅ 现在：同一个中间件实例，Express 和 Socket.io 共享
const sessionMiddleware = session({ ... });
app.use(sessionMiddleware);
setupChat(server, sessionMiddleware); // ← 传进去
```

**必须是同一个实例**——它内部维护着与 MongoStore 的连接，各建一个会导致 session 读取不一致。

### 坑 3：CSP 拦截 WebSocket

```ts
connectSrc: ["'self'", "ws:", "wss:"],
```

helmet 的 CSP 默认不放行 WebSocket 协议，不加这两条浏览器会直接拦截连接。**用 curl 验证不出 CSP 问题**——curl 不执行浏览器安全策略，必须开浏览器实测。

## 九、跨标签页未读提示

### 场景

用户在标签页 A 浏览首页，标签页 B 在聊天室。聊天室收到新消息时，A 页面的"💬 聊天室"导航链接应该闪烁提醒。

### 实现：`localStorage` + `storage` 事件

```js
// 触发方（收到消息且页面不可见时）：
localStorage.setItem('confetti_chat_unread', Date.now().toString());

// 监听方（所有其他标签页自动触发）：
window.addEventListener('storage', (e) => {
  if (e.key === 'confetti_chat_unread' && e.newValue) {
    blinkChatIcon(); // CSS animation: opacity 1 ↔ 0.35 循环
  }
});
```

**注意**：`storage` 事件只在**其他**标签页触发，写入者自己不触发。这是浏览器原生提供的跨标签页通信机制，不需要 SharedWorker 或 BroadcastChannel。

## 十、编码流程复盘（合理的编写顺序）

按**依赖链自底向上**写，每层独立验证：

```
1. Message 模型          → pnpm build 编译通过
2. Socket 服务端骨架      → 启动日志 "💬 聊天 WebSocket 服务已启动"
3. main.ts 集成          → curl /chat → 302（未登录）
4. 控制器 + 路由          → curl -b cookie /chat → 200
5. 模板（chat.ejs 空壳）  → 浏览器看到页面结构
6. _head/_foot 改造      → 导航栏出现聊天链接
7. chat.js 客户端        → Console 显示 "聊天室客户端已就绪"
8. 端到端联调            → 双窗口互发消息
```

**关键原则**：每写完一层立即验证，不要全部写完再启动——否则出问题要排查整个调用链。

## 十一、经验沉淀

1. **协议共存不可怕**：HTTP 和 WebSocket 跑在同一个 Node.js 进程、同一个端口上，共享 Session。关键只是把 `app.listen()` 拆开成 `http.createServer(app)`。

2. **适配器模式无处不在**：`wrapSession()` 本质是把 Express 中间件适配到 Socket.io 的中间件签名。遇到"框架 A 的东西想在框架 B 用"，先想能不能写个薄包装层。

3. **冗余是允许的**：`userName` 冗余存储违反数据库范式，但聊天场景读远多于写，且用户名变更极少——实用主义优先。

4. **预留字段成本低**：`courseId` 字段 + 复合索引现在没用到，但为课程群聊（Rooms 加分项）埋好了路。模型设计时想一步，省得以后改表。

5. **安全是设计出来的**："谁做判断，谁拿身份"——客户端需要身份做 UI 判断时，通过 Socket 握手推送，而不是写在 HTML 里。不在源码里留下 `window.currentUserId` 这种明晃晃的攻击面。

6. **验证要用真实浏览器**：CSP、WebSocket 握手、cookie 携带这些行为 curl 都测不出来，必须开浏览器实测。
